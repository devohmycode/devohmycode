# Propositions pour la version 0.2.0

Objectif : enrichir le profil GitHub avec des statistiques utiles, compréhensibles et reproductibles, tout en conservant le portrait ASCII et la carte compacte claire/sombre.

Ce document est une feuille de route proposée : les cases représentent du travail restant, pas des fonctionnalités déjà disponibles. Les choix ci-dessous privilégient Python 3.12+, la bibliothèque standard et les collecteurs existants de `update_profile.py`.

## Point de départ

- `README.md` affiche les deux variantes de la carte, au format 840 × 500.
- `PROFILE.md` explique la personnalisation, les sources et leurs limites.
- `update_profile.py` collecte les dépôts, étoiles, abonnés, contributions, commits et variations historiques de lignes, puis génère les SVG.
- `test_update_profile.py` couvre déjà plusieurs filtres, la pagination, le calendrier, l'âge, le rendu et la conservation des cartes après un échec de collecte.
- `.github/workflows/update.yml` teste et régénère les cartes chaque jour, puis commit uniquement les deux SVG.

Les périmètres diffèrent : les contributions du calendrier public peuvent inclure des comptes privés anonymisés ; les commits sont filtrés par dépôt ; les lignes concernent l'historique attribué au compte sur les branches par défaut des dépôts publics possédés hors forks. L'année affichée `2022` est personnalisée, alors que la collecte historique commence à la création du compte.

## Règles communes

- **Priorités :** P0 = fiabilité et définitions ; P1 = enrichissements principaux ; P2 = compléments à réaliser après le socle. La priorité ne remplace pas les dépendances.
- **Dépendances :** une tâche commence lorsque toutes les tâches indiquées sont terminées. « Aucune » signifie qu'elle peut démarrer immédiatement. Les liens sont directs ; leurs dépendances sont transitives.
- **Dates :** figer un instant de collecte UTC commun. Les fenêtres de 30/365 jours couvrent des dates calendaires complètes, jusqu'à la veille de la date de collecte. Conserver les dates journalières fournies par GitHub ; ne pas les reconstruire à partir des heures des commits.
- **Confidentialité :** publier uniquement des données de dépôts publics. Seuls les agrégats privés anonymisés déjà visibles sur le calendrier public peuvent contribuer aux métriques de calendrier, avec une mention explicite. Un jeton local plus privilégié ne doit jamais enrichir le résultat publié avec des informations privées.
- **Exactitude :** une source manquante, tronquée ou incohérente provoque un échec avant publication ; aucun remplacement silencieux par zéro. L'absence de référence historique est un état attendu, affiché « historique insuffisant ».
- **Validation :** chaque tâche comportant du calcul ou une nouvelle collecte inclut ses tests ciblés dans `test_update_profile.py`, avec réponses simulées et date fixe. Les tests automatiques ne dépendent ni du réseau ni d'un jeton.
- **Affichage :** mêmes valeurs dans les deux thèmes, échappement XML/Markdown adapté au contexte, valeurs complètes dans le rapport et la description accessible. Les nombres ne sont pas présentés comme un score de qualité ou de maîtrise.
- **Structure :** conserver les fonctions et conventions existantes ; aucun framework, service externe, base de données ou découpage en modules sans besoin démontré.

## Hors périmètre proposé

- Classement global, note de développeur, estimation du temps de travail ou score de productivité.
- Volume exact du code actuellement présent : les variations historiques de lignes ne permettent pas de le déduire.
- Pourcentages de langages attribués personnellement à l'auteur ; le comptage de dépôts par langage principal suffit ici.
- Dashboard hébergé, base de données, suivi de visiteurs ou service de badges tiers.
- Refonte du portrait ou de son outil Pillow : les améliorations portent sur les données et leur présentation.

## Critères de réussite

- Chaque nouvelle statistique possède une définition, une source, une période et des tests de ses limites.
- Les totaux actuels restent présents, avec des libellés explicites et les mêmes exclusions documentées.
- Les deux cartes restent lisibles et cohérentes ; les détails et liens sont accessibles depuis `STATS.md` et `README.md`.
- Une collecte incomplète ou une erreur gérée de publication conserve la dernière génération cohérente.
- Les tests de PR fonctionnent sans secrets ; la génération quotidienne respecte le budget du workflow et ne publie aucun détail privé.
